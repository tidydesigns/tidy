# Editor performance: October 2026

Implementation branch: `perf/editor-incremental-processing`. Baseline: `dddb3f4` from `origin/main`. The DOM/CSS rendering architecture and editor interactions remain in place.

## Results

These are local synthetic workloads, not deployed application or multiplayer measurements. Values are medians of per-run percentiles, rather than pooled samples. Lower is better.

Production-build Chromium, 4× CPU throttling, 60 measured nudges after 10 warmups per case, two runs per version in baseline/optimized/optimized/baseline order:

| Nodes | Baseline median edit | Optimized median edit | Speedup | Baseline p95 | Optimized p95 |
| ----- | -------------------: | --------------------: | ------: | -----------: | ------------: |
| 100   |             48.30 ms |              39.85 ms |   1.21× |     69.95 ms |      48.75 ms |
| 1,000 |            161.40 ms |              51.25 ms |   3.15× |    198.55 ms |      75.85 ms |
| 5,000 |            656.25 ms |             129.10 ms |   5.08× |    808.20 ms |     156.00 ms |

At 5,000 nodes the measured median fell 80.3%. Aggregate browser task time across the 70 nudges fell from 48,329.95 to 9,933.35 ms; script time fell from 32,560.55 to 7,941.95 ms. Mount counts remained bounded at 300 artwork nodes and 33 layer rows for larger documents.

The latency proxy measures a synthetic key event through a changed DOM position and the next animation frame. It does not measure GPU presentation, hardware input latency or real-user INP. Local fixture commits include canonical processing; deployed HTTP, database and collaborative acknowledgment costs are excluded.

Bun kernel, 80 measured operations after 10 warmups, three runs per version in baseline/optimized/optimized/baseline/baseline/optimized order:

| Workflow                                   | Baseline median | Optimized median | Speedup | Baseline p95 | Optimized p95 |
| ------------------------------------------ | --------------: | ---------------: | ------: | -----------: | ------------: |
| Sparse committed edit, 100 nodes           |        3.878 ms |         0.720 ms |   5.39× |     6.815 ms |      1.583 ms |
| Sparse committed edit, 1,000 nodes         |       17.532 ms |         3.697 ms |   4.74× |    27.759 ms |      5.178 ms |
| Sparse committed edit, 5,000 nodes         |      111.611 ms |        24.425 ms |   4.57× |   163.390 ms |     34.148 ms |
| Master edit propagating to 1,499 instances |      109.561 ms |        83.234 ms |   1.32× |   209.381 ms |    119.332 ms |

Sparse edits include change preparation, diffing and patch application. Each operation checks its result. Revalidating the exact already-owned immutable snapshot became a WeakSet lookup: measured values rounded below 0.001 ms at 1,000 and 5,000 nodes, versus baseline medians of 7.769 and 38.513 ms. This is a reuse shortcut for previously validated state, not faster validation of arbitrary inputs.

## Tradeoffs and limits

- Navigation through first selection increased from 1,685 to 1,792 ms at 100 nodes, 1,787 to 2,089 ms at 1,000, and 3,133.5 to 3,693 ms at 5,000. This includes startup, fixture loading, framing and selection, with only two loads per version. Deep freezing and initial cache setup have costs. These measurements do not establish a precise cold-start distribution.
- Pure move-preview medians increased from 0.186 to 0.349 ms at 1,000 nodes and 0.651 to 0.966 ms at 5,000. The complete committed workflow improved substantially, but the standalone preview did not.
- For 120 pan events, aggregate task time was 1,627.70 → 1,733.85 ms at 100 nodes, 1,426.55 → 1,516.90 ms at 1,000 and 1,924.75 → 1,732.65 ms at 5,000. Script time was 725.15 → 782.20, 775.80 → 807.10 and 1,305.95 → 1,051.40 ms respectively. Panning is not a consistent win.
- The original mutable parser remains the default outside editor opt-in paths. Mixed-workload controls were slower on the optimized checkout (5,000-node median 37.012 → 46.771 ms). Separate fresh-process mutable-only controls showed near-identical medians (33.913 → 34.168 ms), but a worse optimized p95 (40.206 → 46.446 ms). Runtime shape/allocation effects and desktop variability matter; this work does not claim faster server validation or prove statistical equivalence.
- Both versions ran on the same AMD Ryzen 5 3600 desktop, Bun 1.4.2 and Chromium 151.0.7922.34, with Next 16.3.8 and React 19.2. No builds, test suites or other owned benchmark browsers ran concurrently with the final browser measurements. Other desktop activity was not controlled. No confidence intervals, real-user telemetry, memory/GC profiling, mobile-device measurements or deployed multiplayer stress tests were collected.
- Editing at 5,000 nodes still exceeds a 16.7 ms frame budget under 4× throttling. These gains do not make every large-document interaction frame-perfect.

## Implementation

1. Added an editor-only immutable document parser. Parser-owned snapshots and unchanged nodes retain identity. Inputs from transport still pass schema validation. A bounded 5,000-entry weak-reference cache reuses exactly equal validated nodes; recursively frozen nested values prevent mutation. New document states still pass all graph invariants. Equivalent complete snapshots can reuse an already-validated document.
2. Threaded that parser through editor edits, optimistic patch application, canonical acknowledgments and revisions. Existing mutable APIs retain their original default parser and ownership semantics.
3. Cached artwork subtrees before descending into unchanged children. Dirty tracking covers changed nodes, old and new ancestor chains, selection, editing, crop state and tokens. Offscreen invalidations persist until a branch is rebuilt. Parent identity, order and responsive width still participate in reuse checks.
4. Replaced repeatedly copied sibling-index arrays in vector processing with linear-time append construction. Regenerated both embedded render runtimes using existing generators.

The approach follows measured hot paths: reduce repeated cloning/validation and preserve identities before adding more rendering machinery. [Zod documents that parsing produces a deep clone](https://zod.dev/basics); [React memoization relies on prop identity](https://react.dev/reference/react/memo). Browser task/script/layout/style measurements distinguish JavaScript savings from browser layout work, following [web.dev's guidance on diagnosing layout cost](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing).

## Functional verification

- `bun typecheck`, `bun lint`, `bun test`, and `bun run build` passed. Web test summary: 801 passed, 665 skipped, zero failures, 14,358 assertions. Database-gated tests were skipped because no local test database was available; no production database was accessed.
- Added immutable-parser mutation, transport-equivalence, schema/graph dependency, 120-transaction reference-equivalence, undo and concurrent-queue tests.
- Added artwork identity/invalidation tests, including reparenting, deletion, offscreen edits and 100 varied branch states compared with fresh construction.
- Existing browser checks passed for component instances, override reset/swap/detach, one-step undo, cross-page navigation, viewer permissions, paints/blends/crop/export/upload, large-document virtualization and keyboard navigation.
- Native shape browser checks passed on two optimized runs and one baseline run. One earlier optimized run timed out during arrow resize/undo; it did not reproduce. Its cause was not established.
- Benchmark assertions checked exact committed movement, component propagation, pan transform changes, bounded mounts and zero page errors.

These checks found no reproducible functional regression in the exercised paths. They do not establish exhaustive compatibility across every document or concurrent editing scenario.

## Reproduction and raw data

Run workspace commands from the repository root. Install the lockfile dependencies in both checkouts. Keep the same harness, dependency versions and production fixture gate in both versions.

```bash
EDITOR_BENCH_ROOT=/path/to/baseline EDITOR_BENCH_OUTPUT=/tmp/kernel-baseline.json bun apps/web/scripts/benchmark-editor-kernel.ts
EDITOR_BENCH_OUTPUT=/tmp/kernel-optimized.json bun apps/web/scripts/benchmark-editor-kernel.ts
EDITOR_BENCH_CONTROL_ONLY=1 EDITOR_BENCH_ROOT=/path/to/baseline bun apps/web/scripts/benchmark-editor-kernel.ts
EDITOR_TEST_URL=http://localhost:3117 EDITOR_BENCH_OUTPUT=/tmp/browser-baseline.json bun apps/web/scripts/benchmark-editor-browser.ts
EDITOR_TEST_URL=http://localhost:3118 EDITOR_BENCH_OUTPUT=/tmp/browser-optimized.json bun apps/web/scripts/benchmark-editor-browser.ts
```

For production browser runs, build each web checkout with the same local configuration, then start each on its respective loopback port with `TIDY_LOCAL_PERFORMANCE_FIXTURES=1`. The baseline needs the identical diagnostic-only change in `apps/web/app/dev/performance-preview/page.tsx`: allow the fixture outside development only with that explicit flag and a localhost/127.0.0.1 Host. Both versions otherwise use their own application code. The committed gate remains off by default; no deployment was performed.

Local build configuration used `BETTER_AUTH_URL` at the respective localhost port, a synthetic local secret, `DATABASE_URL=postgresql://benchmark:benchmark@127.0.0.1:1/benchmark`, `POSTHOG_TRACING_ENABLED=0`, and `WXT_BELLA_URL=https://localhost` for the root extension build. Browser routing blocked external requests, auth/API access and file prefetches. This configuration intentionally provides no working database. Worktree environment symlinks point to the primary checkout; a temporary empty ignored env file was used where no local file existed.

Raw JSON is in [editor-2026-10/](./editor-2026-10/): three kernel files per version, two independent mutable-control files per version and two browser files per version. Scripts: [kernel harness](../../apps/web/scripts/benchmark-editor-kernel.ts), [browser harness](../../apps/web/scripts/benchmark-editor-browser.ts).
