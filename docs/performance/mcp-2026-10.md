# MCP performance, October 2026

The [second pass](mcp-workflows-2026-10.md) adds component algorithm profiling, atomic multi-layer edits, sustained load tests, and browser-to-MCP design validation.

Measured on October 10, 2026 against main at `1caca4c3416fccfe178ebabbb92e5c83a62d00ec`. The optimized implementation keeps the existing TypeScript API and MCP SDK. It removes repeated authorization round trips, schema conversion, workspace serialization of audited reads, and unnecessary full-document work. These local results demonstrate substantial improvements; they do not establish a universal optimum or production capacity.

Throughput in the five-concurrent document scenario rose from 49.28 to 538.49 requests/second. The simulated Linear scenario rose from 7.71 to 41.54 requests/second. These are achieved rates for these closed-loop workloads, not saturation limits or production capacity estimates.

Legacy tool discovery fell from 824,282 to 267,394 response bytes (67.6% smaller). Modern discovery similarly fell from 824,404 to 267,521 bytes. Schema references preserve runtime validation and the exposed tools; no caller data or authorization decision is cached.

The optional `patch_document` argument `include_document: false` returned 559 bytes instead of 1,963,213 bytes and measured 42.49 ms median / 49.20 ms p95. This is a different response contract and is therefore separate from the before/after comparison. The default remains the full document. Component propagation can affect other nodes; callers needing those changes must re-read the document.

## Implementation and correctness

- **Authorization:** verify the token once, parse the bounded body once, and check additional scopes against those verified claims. Reuse that parsed body in the SDK. Consolidate persisted grant checks into dependent materialized CTEs, preserving user/client/resource/link/session/consent lock order. The shared consent gate remains a separate SQL statement so the following statement obtains a fresh snapshot after any wait. Grant checks remain uncached, with clock and authority revalidation before commit/publication.
- **Concurrency:** only an explicit allowlist of audited read handlers runs outside the outer MCP transaction. A short final transaction retains and checks current authority and targets before publishing the result. Remote reads no longer hold the outer workspace gate or its database connection across provider I/O. Unknown tools and operations that reconcile or update records retain the atomic write path. In particular, GitHub review-context/feedback reconciliation and import validation are not classified as pure reads. Individual services retain their own transaction and authorization logic.
- **Metering and atomic writes:** quota admission remains independently committed; rejected or revoked work still consumes its admitted call. Writes retain the workspace gate, target locks, nested savepoints, optimistic revision checks, and rollback behavior. Organization-level quota coordination is deliberately retained for correctness.
- **Discovery:** retain a fresh SDK server and caller-bound handlers per request; cache only static deployment-owned Zod schemas and their JSON Schema conversions. JSON Schema uses local `$defs` references for repeated structures. Modern discovery responses carry private five-minute cache hints. Both SDK JSON Schema validators are tested against the emitted references, and modern recursive tool calls are exercised through the real route.
- **Documents:** paginated reads project the requested nodes and metadata in PostgreSQL instead of transferring, decoding, and scanning the entire document in JavaScript. Single-node edits remove one redundant full validation pass; final graph validation and asset authorization still run. Compact edit responses are opt-in and preserve revision handling.
- **Realtime and tracing:** advisory Cloudflare activity delivery uses `waitUntil`; terminal activity still starts after database commit. Add bounded request/body/authorization/admission/workspace-lock/execution/publication spans. Keep legacy POST SSE traces alive until the response stream completes so database and tool spans are not cut off at response headers. Stream contents are neither buffered nor logged by this observer.

The implementation uses the installed `@modelcontextprotocol/server` 2.1.0 support for the July 28, 2026 protocol, while retaining legacy June 18, 2025 HTTP compatibility. Its request-local server lifecycle and parsed-body handling follow the [SDK HTTP guidance](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/http.md) and [stateless scaling guidance](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/sessions-state-scaling.md). Modern routing and discovery behavior are covered by integration tests; see the [July 2026 protocol release](https://blog.modelcontextprotocol.io/posts/2026-07-28/) and [Streamable HTTP specification](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx).

## Reproduce locally

Environment: Apple M5, macOS arm64, Bun 1.3.14, PostgreSQL 17.11, Node 26.7.0. Install the repository's locked dependencies and ensure local PostgreSQL binaries are available to the existing disposable database runner. Run from the repository root:

```sh
bun install --frozen-lockfile
MCP_BENCHMARK_SAMPLES=100 MCP_BENCHMARK_COMPACT=1 \
  MCP_BENCHMARK_OUTPUT=/tmp/mcp-optimized.json bun run bench:mcp
MCP_BENCHMARK_SAMPLES=20 MCP_BENCHMARK_QUERY_DELAY_MS=5 \
  MCP_BENCHMARK_OUTPUT=/tmp/mcp-optimized-delay.json bun run bench:mcp
bun run test:mcp:db
```

The runner creates a disposable loopback PostgreSQL cluster and runtime role, installs fixture schema/data, and tears the cluster down. It never uses a production database. The benchmark starts the actual authenticated MCP POST handler with `Bun.serve` on loopback and exercises it over HTTP. Token signing happens outside measurement; token verification, database authorization, quota admission, SDK routing, business operations, and full response consumption happen inside measurement. JWKS and external-provider fetches use local fixtures. The Linear provider fixture waits 100 ms and returns synthetic data; it makes no real provider requests.

The baseline was run in a separate worktree at the main commit above with only the benchmark harness added. To reproduce it, copy `apps/web/scripts/test-account-controls.mjs`, `apps/web/lib/mcp/grants.integration.test.mjs`, `apps/web/lib/mcp/performance-benchmark.mjs`, and `apps/web/lib/mcp/linear-read-fixture.mjs` from this revision into that worktree, install its locked dependencies, and invoke `node apps/web/scripts/test-account-controls.mjs --mcp-benchmark` with the same environment variables (omit `MCP_BENCHMARK_COMPACT`). In benchmark mode the integration module registers only the benchmark; optimized-only test bodies are skipped.

SQL counts include all application statements, including transaction control and lock statements, and exclude fixture-admin queries. Each recorded run is one warmed local run, with no concurrent builds or test suites. There are no confidence intervals or sustained-load/cold-start claims. Ordinary scenarios use legacy MCP, with modern discovery measured separately and modern tool execution covered by integration tests.

## Verification and remaining limits

The MCP database suite passes 142 tests / 832 assertions, including revocation during body parsing and remote reads, expiry while waiting, account/client/resource/consent controls, target movement, provider credential invalidation, quota charging, concurrent reads and writes, malformed input, pagination, compact responses, stale revisions, and graph-validation rollback. The auth (28), account (98), Linear (47), GitHub (75), and multiplayer (21) database suites also pass. Type checking, formatting/lint, the full unit suite (731 passed, 652 database-gated tests skipped), the standard production build, the OpenNext Worker build, and release tests pass. Dependency audit completes with the repository's existing documented tooling advisory; this change does not alter dependencies.

Hosted Next/OpenNext routing, Cloudflare CPU and cold starts, Hyperdrive/database geography, R2 and Durable Object latency, real provider APIs, and production load are not measured by this local harness. The realtime scheduling change is regression-tested but its hosted latency benefit is not quantified. No deployment or production configuration was changed.

The remaining large-document edit cost includes complete graph validation, JSON serialization, JSONB storage, and (by default) returning the full document. This remains proportional to document size and can still be a bottleneck. Faster language execution alone would not remove that data-model cost or network waits. Before considering Rust, use the new hosted traces to distinguish CPU, lock waits, database round trips, and provider time, and measure representative document sizes and concurrency. Cloudflare documents [database-aware placement](https://developers.cloudflare.com/workers/configuration/placement/) and separate [CPU versus wall-time metrics](https://developers.cloudflare.com/workers/observability/metrics-and-analytics/); placement changes require an explicit deployment decision. Rust on the current Workers platform would run as [WebAssembly](https://developers.cloudflare.com/workers/languages/rust/), so a native-server benchmark would not establish its benefit here.
